# Event Core Engine 情报分析能力路线图

## 1. 定位

Event Core Engine 的目标不止是保存结构化事件，还要把连续的公开信息转换为可比较、可追踪、可解释和可预警的情报状态。

引擎应围绕以下对象逐层构建能力：

```text
EventRecord      单篇消息中的一次事件观察
    ↓
CanonicalEvent  同一现实事件的稳定身份及状态演化
    ↓
EventEpisode    由多个独立事件组成的危机、战争、项目或政策周期
    ↓
Indicator       从事件和 Episode 计算出的趋势、异常及风险指标
    ↓
Alert           达到规则或阈值后形成的可解释预警
    ↓
Assessment      基于证据、冲突和指标形成的态势判断
```

`Claim` 与 `Evidence` 横跨以上各层，用于说明每项事实来自哪里、由谁主张、有哪些支持或反驳证据。

## 2. 设计原则

1. `EventRecord` 是来源对现实事件的一次观察，不直接等同于已确认事实。
2. 原始观察不可覆盖；聚合、绑定和研判结果必须能够重建和修正。
3. `CanonicalEvent` 只合并同一现实事件。相关事件、因果事件和组成事件通过 Relation 或 Episode 连接。
4. 未知不等于冲突；缺失信息不能作为事实不一致的证据。
5. 所有自动合并、状态更新、指标和预警必须给出可读原因与支撑事件。
6. 结构化规则承担确定性计算，AI 用于抽取、辅助匹配和生成说明，不能隐藏关键判断依据。
7. 误合并成本高于暂不合并，默认采用保守策略。

## 3. 核心能力

### 3.1 事件增量与状态演化

把新观察与已有 `CanonicalEvent` 比较，输出：

- `new_event`：新的现实事件。
- `duplicate_observation`：没有实质增量的重复报道。
- `state_update`：阶段、授权、意图或其他状态发生变化。
- `fact_update`：时间、地点、参与者、数值等事实得到补充或修正。
- `conflicting_observation`：与已有观察存在明确冲突。
- `ambiguous`：信息不足，需要人工复核。

每次比较都应产生字段级差异，例如：

```text
phase: planned -> completed
authorization: pending -> approved
amount: USD 4.2B -> USD 4.5B
deadline: unknown -> 2026-12-31
```

该能力可为重复过滤、新颖性评分、摘要生成和重点事件追踪提供确定性依据。

### 3.2 实体注册与行为档案

建立跨文件、跨来源的实体注册表，统一名称、别名和全局 UUID。支持：

- 实体做过什么、正在做什么。
- 实体遭受过哪些行动或影响。
- 实体与哪些主体频繁互动。
- 实体在不同事件中承担的角色变化。
- 按时间、地点、谓词和 Episode 生成行为时间线。

实体合并必须保留别名、来源、匹配理由、置信度和拆分历史。

### 3.3 EventEpisode

`EventEpisode` 表示由多个独立事件组成的长期过程，例如战争、边境危机、并购交易、建设项目、疫情或政策周期。

Episode 应包含：

- 类型、名称和稳定 UUID。
- 成员 CanonicalEvent 及其加入理由。
- 参与主体、受影响对象和活动区域。
- 起止时间、当前阶段和最近关键变化。
- 事件频率、严重程度与地理扩散趋势。
- 支撑当前阶段判断的事件和证据。

Episode 绑定应可人工修正，并允许一个事件参与多个不同观察视角的 Episode。

### 3.4 实体—事件图谱

以事件作为独立节点保存多元角色关系：

```text
组织A --actor------> Event
设施B --target-----> Event
装备C --instrument-> Event
地区D --location---> Event
```

主体—谓词—客体是便于查询和展示的投影，底层继续保留完整角色、时间、地点、数值、限定词和来源。

图谱应支持：

- 单实体行为、遭遇和关联对象查询。
- 多跳路径与共同参与关系查询。
- 高频目标、重复行动者和关键中介识别。
- 供应链、组织隶属和地域扩散分析。
- CanonicalEvent、Episode、Claim 和 Evidence 的关系导航。

### 3.5 指标与预警

指标由结构化事件计算，预警由规则、阈值或基线异常触发。每项结果必须包含支撑事件和触发原因。

候选指标包括：

- 某谓词在时间窗口内的频率和增长率。
- 新参与主体、新地区或新工具出现。
- 行动范围、损失、金额和持续时间变化。
- `planned -> approved -> completed` 等关键状态跃迁。
- 事件地理密度、扩散速度和热点迁移。
- 同一对象受到多主体连续作用。
- 来源数量、独立确认数量和冲突比例。

典型规则：

```text
attack 频率显著上升
+ 出现新的 belligerent
+ deploy 扩展到新地区
=> 区域冲突升级预警
```

```text
sanction 或 restrict
+ supply 减少
+ shortage 出现
=> 关键资源供应风险
```

```text
outbreak
+ 医疗资源 shortage
+ affected_area 扩大
=> 公共卫生升级预警
```

### 3.6 Claim、Evidence 与来源冲突

事件字段应能追溯到具体主张和证据。建议记录：

- 来源、文章 UUID 和原始链接。
- 支撑实体、角色、时间、数值或限定词的原文片段。
- 发布时间、采集时间和观察时间。
- 第一手、转载、引述或匿名来源属性。
- 来源可信度与抽取置信度。
- 支持、反驳、修正或仅转述另一主张。
- 独立来源数量和来源依赖关系。

引擎应允许相互冲突的观察同时存在，通过物化视图给出当前判断，而不是覆盖原记录。

### 3.7 风险传播与影响路径

在明确关系和规则支撑下计算事件影响路径，例如：

```text
出口限制
  -> 原材料供应下降
  -> 制造能力受限
  -> 产品价格上涨
```

每条传播路径应区分：

- 正文明确表达的关系。
- 多来源共同支持的关系。
- 规则推导的候选关系。
- 尚待验证的分析假设。

推导结果必须记录使用的规则、输入事件、时间窗口和置信度。

### 3.8 情报缺口与采集建议

根据事件完整度、价值和冲突情况生成待确认问题：

- 主体、目标、时间或地点缺失。
- 数值只有单一来源支持。
- 高价值事件缺少官方或独立来源确认。
- 计划、授权或行动长期没有后续状态。
- 影响对象和运行状态未知。
- 冲突观察尚未解决。

缺口可以转化为监控条件、搜索任务或人工研判清单，从而形成“分析发现缺口—采集补充信息—状态更新”的闭环。

### 3.9 结构化检索与可解释问答

查询应优先使用谓词、角色、实体、时间、地点、限定词和属性进行精确过滤，再结合向量检索处理语义近似。

目标问题包括：

- 某组织最近实施了哪些行动？
- 哪些设施反复成为攻击目标？
- 某国对哪些主体实施过制裁或限制？
- 哪些主体同时参与军事部署与外交谈判？
- 某资源短缺之前出现了哪些供应、运输或监管事件？
- 哪些地区正从偶发袭击转为持续冲突？

生成式回答必须引用具体 EventRecord、CanonicalEvent 和 Evidence。

## 4. 推荐实施顺序

### 阶段一：可靠事件身份

1. 为全部谓词补充 CanonicalEvent 身份规则。
2. 实现字段级事件差异与增量分类。
3. 实现 CanonicalEvent 的持久化、绑定和重算。
4. 建立跨文件实体注册与别名解析。

完成标准：同一现实事件的计划、批准、执行和完成观察可以形成一条可解释状态轨迹；重复和冲突观察能够区分。

### 阶段二：持续态势

1. 实现 EventEpisode 领域模型和成员绑定。
2. 构建事件时间线、主体客体图谱和地理聚合。
3. 形成实体档案和 Episode 当前状态视图。

完成标准：可以从分散事件自动形成持续更新的危机、项目或政策过程，并能解释成员事件为何被纳入。

### 阶段三：监测与预警

1. 建立指标计算框架和历史基线。
2. 提供声明式规则和预警生命周期。
3. 支持频率突增、范围扩散、状态跃迁和异常组合。

完成标准：每项预警包含触发条件、指标值、支撑事件、置信度和解除条件。

### 阶段四：证据与高级研判

1. 增加 Claim、Evidence、来源依赖和冲突消解。
2. 实现风险传播路径和分析假设管理。
3. 生成情报缺口、采集建议和可解释问答。

完成标准：任何事实、推导和研判都能回溯到来源、观察、规则和版本。

## 5. 当前最高优先级

下一项建议实现“事件增量与状态演化引擎”。它直接使用现有 EventRecord、Qualifier、属性和 CanonicalEvent，在保持引擎独立的前提下，最早产生以下价值：

- 识别重复报道。
- 找出当前消息相对历史的新增事实。
- 跟踪计划、批准、执行、完成、取消和否认。
- 检测数值、时间、角色和状态冲突。
- 为新颖性评分和后续预警提供结构化依据。
