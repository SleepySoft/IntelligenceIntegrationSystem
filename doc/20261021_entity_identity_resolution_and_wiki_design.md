# 实体身份解析、上下文指称与实体 Wiki 设计讨论

> 日期：2026-10-21  
> 状态：设计基线；MVP 已于 2026-10-21 实施
> 相关模块：`EntityAlias/`、`SituationViews/`、Event V4 实体抽取与投影  
> 前置文档：`doc/20261016_entity_alias_subsystem.md`

## 1. 背景与问题

现有 `EntityAlias` 解决的是“一个全局实体具有多个确定名称”的问题，但实际情报中的
实体处理还包含另外两类问题：需要上下文才能消歧的专名，以及只在特定情报或事件中
成立的泛称。如果把三类名称都放进全局别名表，会制造错误合并；如果完全不合并，又会
让同一实体在关系图中碎裂成多个节点。

本轮讨论要解决的问题包括：

1. 带有上级、所属地、职务等前缀的实体名如何进一步合并；
2. “抗议者”“示威者”等非标准实体如何处理；
3. 如何建立可供情报阅读者查询背景的实体 Wiki；
4. 如何展示地点所属国家、上级行政区和位置；
5. 如何改善当前实体名称标准化覆盖率极低的问题；
6. 是否允许在实体图中人工选择、合并节点；
7. 如何让依赖上下文的解析记录与具体情报建立可追溯的一对多关联；
8. 解析结果应直接改写情报，还是以非破坏性旁路数据保存。

## 2. 理论基础：名称、指称与实体不是一回事

实体处理中至少存在三个不同对象：

- **名称（name/surface）**：语言中的字符串，例如“肯尼迪”；
- **指称（mention）**：该字符串在某篇情报、某个事件和某个角色槽中的一次出现；
- **实体（entity/referent）**：现实世界中被指向的人、组织、地点或特定群体。

因此，“字符串相同”不能推出“实体相同”，“字符串不同”也不能推出“实体不同”。
实体合并的正确对象是指称所指向的实体身份，而不是字符串本身。

本设计采用以下基本原则：

> 确定性事实可以全局复用；依赖上下文的判断必须绑定证据；不确定时宁可暂不合并。

## 3. 名称与指称的三类语义

### 3.1 确定性别名

例如“美国”“美利坚合众国”“United States”。这些名称之间的等价关系是全局稳定的，
可以保存为：

```text
normalized_name -> ent_*
```

它们适合自动归一化、查询扩展和跨情报图节点合并，继续由 Git 管理的
`EntityAlias/data/*.jsonl` 保存。

### 3.2 依赖上下文的歧义专名

例如“肯尼迪”“华盛顿”“苹果”。这些名称可能对应多个全局实体，不能建立唯一的
全局映射。解析结论必须绑定到具体情报中的指称：

```text
(intelligence ref, mention) -> ent_*
```

例如：

```text
情报 A 中的“肯尼迪”       ─┐
情报 B 中的“约翰·肯尼迪”   ─┼-> ent_jfk
情报 C 中的“肯尼迪总统”     ─┘

情报 D 中的“肯尼迪”         ──> ent_rfk
```

多条指称解析记录可以指向同一个全局实体，所以多篇情报在实体图中仍汇聚为同一个点。

### 3.3 依赖上下文的泛用名词

例如“民众”“示威者”“警方”“当地官员”。它们不是全局实体的别名，绝不能写入全局
别名表，也不能因为名称相同就在不同事件间自动合并。

如果有证据确认多篇报道描述的是同一批人，可以让多个指称共同指向一个上下文实体：

```text
情报 A 中的“示威者”   ─┐
情报 B 中的“抗议人群” ─┼-> ctx_paris_protesters_*
情报 C 中的“游行民众” ─┘
```

这个 `ctx_*` 节点可以跨越多篇情报，但只在被证据限定的文章、事件或事件簇范围内成立；
它不会产生“示威者 -> ctx_*”这样的全局规则。

## 4. 概念模型

系统应明确区分以下概念：

| 概念 | 含义 | 身份范围 |
|---|---|---|
| `Mention` | 情报中的一次实体指称 | 情报/事件/角色槽 |
| `Entity` | 稳定的现实世界实体 | 全局，ID 为 `ent_*` |
| `ContextualEntity` | 经证据关联的特定群体或临时对象 | 指定 ref 集合，ID 为 `ctx_*` |
| `MentionResolution` | 某个指称指向哪个实体的判断 | 绑定具体 ref |
| `EntityFact` | 实体的背景知识及来源 | 全局实体或上下文实体 |
| `EntityRedirect` | 实体合并后的重定向关系 | 全局、可审计、可撤销 |

## 5. 存储边界

### 5.1 JSONL 只保存确定性实体事实

`EntityAlias/data/*.jsonl` 继续保存：

- 稳定全局实体及 `ent_*` ID；
- 标准名和多语言标准名；
- 确定性别名；
- Wikidata 等外部标识；
- 经核实的基础说明。

这些数据不依赖某篇具体情报，适合人工审查、Git diff 和跨部署复用。

### 5.2 歧义专名解析进入数据库

建议使用独立 MongoDB 集合 `<prefix>entity_global_resolutions`，每次指称一条记录：

```json
{
  "mention_id": "mn_*",
  "ref": {
    "subsystem": "news",
    "intelligence_uuid": "...",
    "local_entity_id": "ENT1"
  },
  "surface": "肯尼迪",
  "normalized_surface": "肯尼迪",
  "target_entity_id": "ent_jfk",
  "method": "manual",
  "confidence": 1.0,
  "reason": "...",
  "source_revision": "...",
  "created_at": "...",
  "updated_at": "..."
}
```

目标必须是稳定 `entity_id`，而不是可能变化的标准名或别名字符串。

### 5.3 泛指实体与歧义专名分开存储

泛指实体至少拆为两个集合：

- `contextual_entities`：保存 `ctx_*` 身份、显示名、作用域和说明；
- `<prefix>contextual_entity_resolutions`：保存每个具体指称到 `ctx_*` 的关联。

物理分离的目的，是从数据结构上阻止泛称被误当成全局实体：

```json
{
  "contextual_entity_id": "ctx_*",
  "name": "法国养老金改革示威者",
  "type": "collective",
  "qualifiers": {
    "countries": ["FR"],
    "locations": ["巴黎"],
    "topic": "养老金改革抗议"
  },
  "created_at": "..."
}
```

```json
{
  "mention_id": "mn_*",
  "ref": {
    "subsystem": "news",
    "intelligence_uuid": "...",
    "local_entity_id": "ENT1"
  },
  "surface": "示威者",
  "target_contextual_entity_id": "ctx_*",
  "method": "manual",
  "confidence": 1.0
}
```

不要在实体文档中维护不断增长的 ref 数组。应采用“一次指称一条关联记录”，通过
`target_entity_id` 或 `target_contextual_entity_id` 反向查询全部情报。这样避免并发更新、
文档膨胀和审计困难。

上下文实体只要求用户填写一个便于识别的 `name`。国家、地点、时间、议题和说明等字段
可以预留并由当前情报自动预填，但不得成为创建时的必填负担。名称用于搜索和展示，身份
仍由 `ctx_*` 决定；名称相同不能触发自动合并。

### 5.4 为什么优先使用 MongoDB

当前情报和事件已经存储在 MongoDB。上下文解析数据需要高频完成两个方向的联立：

- 从一批情报/事件批量取得全部指称解析；
- 从一个实体反查支撑它的全部情报。

MongoDB 可以复用现有运维体系、集合前缀和子系统隔离，无需引入 PostgreSQL 等新依赖；
文档结构也适合解析算法逐步增加证据字段。SQLite 仍适合审计或小型工具，但不适合作为
实体图与 Mongo 事件之间的主联立层。

建议索引：

- `mention_id` 唯一索引；
- `ref.intelligence_uuid`；
- `ref.event_uuid`；
- `(ref.subsystem, ref.intelligence_uuid)`；
- `target_entity_id`；
- `target_contextual_entity_id`；
- `(normalized_surface, target_entity_id)`。

## 6. ref 与 mention 的稳定定位

Event V4 已为每篇情报抽取出的实体分配文章内唯一 ID（`ENT1`、`ENT2` 等）。主引用采用：

```text
EntityRef = subsystem + intelligence_uuid + local_entity_id
```

同一 `ENT1` 可以被一篇情报里的多个事件和角色复用，因此它比数组位置更稳定，也避免为
每次角色使用重复登记解析结论。事件查询索引必须保留 `local_entity_id`，当前仅保存名称
快照的实现需要补齐该字段并从权威归档重建。

为处理抽取错误（例如同一个 `ENT1` 被错误地复用于两个现实实体），协议预留更细粒度的：

```text
UsageRef = EntityRef + event_uuid + role + position
```

解析时 UsageRef 优先于 EntityRef。第一阶段不要求界面暴露 UsageRef，只有出现实际拆分需求
时再启用，以免把正常操作复杂化。

在落地时应生成稳定 `mention_id` 或使用复合唯一键，并保存 `source_revision` 或源结构指纹；
如果权威抽取后来被重建，系统应把失配解析标为待复核，而不是静默指向错误位置。

具体的 mention 定位协议、事件修改语义和指纹算法仍属于待讨论项。

## 7. 采用非破坏性解析，不改写原始情报

讨论过两种方案：

1. **破坏性**：把 Event V4 中的实体名称替换为 UUID 引用；
2. **非破坏性**：保留原始抽取，在旁表保存解析关系，读取时形成解析视图。

当前结论是采用非破坏性方案。原因包括：

- 原始名称是 LLM 实际抽取结果，也是判断解析是否合理的重要证据；
- 歧义消解、泛称归组和人工合并以后都可能被推翻；
- 直接替换会破坏 Event V4 的现有存储契约；
- 拆分、撤销和更换权威实体时不应批量改写历史情报；
- 原始数据与解释性投影分离，更符合可追溯的数据处理原则。

读取时可以形成如下解析视图：

```json
{
  "surface": "肯尼迪",
  "resolved_name": "约翰·肯尼迪",
  "entity_id": "ent_jfk"
}
```

如果未来性能不足，可以增加可重建的物化投影或缓存，但该投影不能成为事实源。

当前 Event V4 管线的 `_normalize_entity_names()` 会在归档前直接替换抽取名称，这与上述结论
冲突。落地时应停止覆盖权威 `EVENT_EXTRACTION.entities[].name`；确定性别名也通过解析视图
生效。历史上已经被替换的少量名称保持现状，除非以后依据原文重新抽取。

## 8. 实体图的身份解析规则

实体图不应继续用“名称 + 类型 + 国家”作为最终身份。每个指称按以下优先级解析：

1. 命中当前 ref 的歧义专名记录：使用 `ent_*`；
2. 命中当前 ref 的泛指关联记录：使用 `ctx_*`；
3. 命中全局确定性别名：使用 `ent_*`；
4. 均未命中：按“名称 + 类型 + 国家”生成仅用于显示的 surface 节点。

只要多篇情报中的指称解析到同一 `ent_*` 或 `ctx_*`，它们在图上就是同一个点，事件数、
文章数和关系印证据此累计。图仍应展示每条边和节点背后的原始 ref，以便人工核验。

未解析指称允许在图的显示层按名称临时聚合，以维持可读的关系网络和人工治理入口；这不是
固定别名或身份判断，也不会持久化。若两篇情报中的“示威者”实际不是同一群体，用户可选择
聚合节点背后的具体 EntityRef，分别指定到更明确的 `ctx_*`，刷新后自然拆分。

## 9. 带前缀名称与层级实体

不能通过简单删除前缀实现合并，因为前缀可能只是描述，也可能构成新的实体身份：

- “美国总统特朗普”中的“美国总统”是职务上下文，可以帮助解析到特朗普；
- “法国巴黎市”“巴黎”可能是同一地点的不同表述；
- “北京大学医学部”与“北京大学”是上下级实体，不能作为别名合并；
- “中国银行北京分行”与“中国银行”同样应表达隶属关系而非等价关系。

因此应采用“候选生成 + 上下文验证”：识别头衔、地域和上级组织等修饰成分，再结合实体
类型、时间、国家、共现实体和外部 ID 判断是别名、歧义消解线索，还是独立下级实体。

## 10. 实体外部百科（当前范围）

当前不建设本地实体 Wiki，以免分散实体解析与关系图治理的开发精力。对于已经解析到
`ent_*` 的节点，直接用标准名拼接外部搜索链接：

- 百度百科：`https://baike.baidu.com/search/word?word=<标准名>`；
- 中文 Wikipedia：`https://zh.wikipedia.org/w/index.php?search=<标准名>`。

链接必须 URL 编码并以新窗口打开。上下文实体 `ctx_*` 没有稳定百科对象，默认不显示。
本地实体知识页、结构化地理层级和事实来源模型全部推迟，只有出现明确需求时再设计。

## 11. 人工指定实体、实体合并与作用范围

实体图的常规编辑动作应称为“指定实体”或“解析指称”，而不是“合并”。系统始终把单个
`EntityRef` 指向一个目标；多个 ref 最终指向同一个目标后，图节点自然汇聚。批量选择只是
重复执行同一指定动作的操作便利。

界面和服务契约把“登记目标实体”和“按情报消歧”作为两个独立、可连续执行的动作，而不是
互斥的操作模式：

1. **登记/选择目标实体**：用 radio 选择目标库；全局实体进入 `ent_*`，语境实体进入
   `ctx_*`。新建动作只写目标实体表，不自动关联情报。全局固定别名登记也只修改
   EntityAlias，不接收 EntityRef。
2. **按情报消歧**：选择一个或多个 `EntityRef`，把它们指向前一步选中的目标。既可以使用
   已有目标，也可以刚登记一个目标后立即保存指向；也允许只登记而不做消歧。

因此 radio 只回答“实体录入/指向哪个目标库”，不用于在“登记”和“消歧”之间二选一。
后端以独立端点保证边界：登记接口不接受情报 UUID/EntityRef，消歧接口则必须接受 ref。

“肯尼迪”可以依赖当前情报指向全局的 `ent_jfk`，但不能因此成为其全局固定别名；
“示威者”则指向用户命名的 `ctx_*`。因此“登记一个什么目标”和“哪些情报指向该目标”是
两个动作；目标库存放位置由 radio 明确选择，不能合并成一个含糊的“是否依赖上下文”选项。

只有两个已经存在的 `ent_*` 被确认重复时，才使用严格意义上的“合并实体”，并写入
`EntityRedirect`。这属于低频、高风险的高级治理操作，不与日常指定实体混在一起。

所有人工治理操作都应支持：

- 指定或合并前预览涉及的名称、类型、国家、关系和支撑情报；
- 记录操作者、时间、理由和影响范围；
- 撤销合并、拆分错误实体和重新指派 ref；
- 阻止或强提醒明显的类型冲突；
- 永久保留原始抽取值。

实体合并优先使用 `old_entity_id -> authoritative_entity_id` 重定向，不直接重写全部历史数据。

## 12. 标准化率应如何衡量和提升

当前覆盖率低有两个直接原因：全局别名数据量很小，以及归档侧只有精确命中才会替换名称。
未来不应只统计“不同字符串中多少进入别名表”，而应分别统计：

- 指称加权的确定性别名命中率；
- 歧义专名已解析率、未解析率和人工/自动来源；
- 泛称识别率、已归组率和受保护未合并率；
- 图节点中 `ent_*`、`ctx_*`、surface 临时节点的数量及情报覆盖；
- 人工决定的撤销率和过期解析数量。

提升路径应是：扫描历史和新增情报中的高频未解析指称，形成工作队列；对高置信确定性名称
补入 JSONL，对歧义专名保存 ref 解析，对泛称仅在有证据时归入 `ctx_*`。模糊或向量相似
只用于召回候选，不能单独成为自动合并依据。

## 13. 当前实现与后续差距

截至本文日期，现有实现具有以下限制：

- `AliasIndex._exact` 是“一个标准化名称 -> 一个实体”，同名歧义会被冲突校验拒绝；
- Event V4 权威抽取保留原始名称，不再由别名后处理改写；
- 查询层只进行确定性别名展开；
- `SituationViews` 已接入 EntityRef、全局/语境解析与人工治理；未解析 ref 按名称、类型和国家形成临时显示节点；
- 尚未实现 UsageRef 级拆分、实体重定向和 AI 自动消歧；
- 当前 JSONL 仅有少量实体，不能代表可用的标准化覆盖。

实体重定向、UsageRef 和自动消歧仍是后续能力，不得视为当前已经具备。

## 14. 暂定实施顺序

以下顺序只作为后续落地讨论的起点：

1. 以 `subsystem + intelligence_uuid + local_entity_id` 定义 EntityRef，预留 UsageRef；
2. 实现非破坏性解析存储、反向查询和审计；
3. 让实体图优先使用 `ent_*` / `ctx_*`，未解析节点保持 ref 作用域；
4. 实现图上的单 ref“指定实体”、上下文实体搜索/新建及撤销；
5. 改造全局名称索引，使歧义名可以召回多个候选但不能自动唯一解析；
6. 建立高频未解析指称工作队列和历史投影重建；
7. 建设实体 Wiki，先完善地理实体；
8. 在数据和人工反馈充分后，再引入自动上下文消歧。

## 15. 后续仍需讨论的落地问题

1. `mention_id` 使用确定性 ID 还是 Mongo 复合唯一键；
2. 三类 Mongo 集合是全局集合带 `subsystem`，还是沿用子系统集合前缀；
3. 原始事件修订后如何识别并处理过期解析；
4. `ctx_*` 的允许作用域、跨文章归组条件和生命周期；
5. 图查询时实时联立还是维护可重建物化投影；
6. 全局实体合并重定向、拆分和循环检测协议；
