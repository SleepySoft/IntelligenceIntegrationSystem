# 实体身份解析、上下文指称与实体 Wiki 设计讨论

> 日期：2026-10-21  
> 状态：设计讨论基线，尚未实施  
> 相关模块：`EntityAlias/`、`SituationViews/`、Event V4 实体抽取与投影  
> 前置文档：`doc/20261016_entity_alias_subsystem.md`

## 1. 背景与问题

现有 `EntityAlias` 解决的是“一个全局实体具有多个确定名称”的问题，但实际情报中的
实体处理还包含另外两类问题：需要上下文才能消歧的专名，以及只在特定情报或事件中
成立的泛称。如果把三类名称都放进全局别名表，会制造错误合并；如果完全不合并，又会
让同一实体在关系图中碎裂成多个节点。

本轮讨论要解决的问题包括：

1. 带有上级、所属地、职务等前缀的实体名如何进一步合并；
2. “抗议者”“示威者”等非标准实体如何处理；
3. 如何建立可供情报阅读者查询背景的实体 Wiki；
4. 如何展示地点所属国家、上级行政区和位置；
5. 如何改善当前实体名称标准化覆盖率极低的问题；
6. 是否允许在实体图中人工选择、合并节点；
7. 如何让依赖上下文的解析记录与具体情报建立可追溯的一对多关联；
8. 解析结果应直接改写情报，还是以非破坏性旁路数据保存。

## 2. 理论基础：名称、指称与实体不是一回事

实体处理中至少存在三个不同对象：

- **名称（name/surface）**：语言中的字符串，例如“肯尼迪”；
- **指称（mention）**：该字符串在某篇情报、某个事件和某个角色槽中的一次出现；
- **实体（entity/referent）**：现实世界中被指向的人、组织、地点或特定群体。

因此，“字符串相同”不能推出“实体相同”，“字符串不同”也不能推出“实体不同”。
实体合并的正确对象是指称所指向的实体身份，而不是字符串本身。

本设计采用以下基本原则：

> 确定性事实可以全局复用；依赖上下文的判断必须绑定证据；不确定时宁可暂不合并。

## 3. 名称与指称的三类语义

### 3.1 确定性别名

例如“美国”“美利坚合众国”“United States”。这些名称之间的等价关系是全局稳定的，
可以保存为：

```text
normalized_name -> ent_*
```

它们适合自动归一化、查询扩展和跨情报图节点合并，继续由 Git 管理的
`EntityAlias/data/*.jsonl` 保存。

### 3.2 依赖上下文的歧义专名

例如“肯尼迪”“华盛顿”“苹果”。这些名称可能对应多个全局实体，不能建立唯一的
全局映射。解析结论必须绑定到具体情报中的指称：

```text
(intelligence ref, mention) -> ent_*
```

例如：

```text
情报 A 中的“肯尼迪”       ─┐
情报 B 中的“约翰·肯尼迪”   ─┼-> ent_jfk
情报 C 中的“肯尼迪总统”     ─┘

情报 D 中的“肯尼迪”         ──> ent_rfk
```

多条指称解析记录可以指向同一个全局实体，所以多篇情报在实体图中仍汇聚为同一个点。

### 3.3 依赖上下文的泛用名词

例如“民众”“示威者”“警方”“当地官员”。它们不是全局实体的别名，绝不能写入全局
别名表，也不能因为名称相同就在不同事件间自动合并。

如果有证据确认多篇报道描述的是同一批人，可以让多个指称共同指向一个上下文实体：

```text
情报 A 中的“示威者”   ─┐
情报 B 中的“抗议人群” ─┼-> ctx_paris_protesters_*
情报 C 中的“游行民众” ─┘
```

这个 `ctx_*` 节点可以跨越多篇情报，但只在被证据限定的文章、事件或事件簇范围内成立；
它不会产生“示威者 -> ctx_*”这样的全局规则。

## 4. 概念模型

系统应明确区分以下概念：

| 概念 | 含义 | 身份范围 |
|---|---|---|
| `Mention` | 情报中的一次实体指称 | 情报/事件/角色槽 |
| `Entity` | 稳定的现实世界实体 | 全局，ID 为 `ent_*` |
| `ContextualEntity` | 经证据关联的特定群体或临时对象 | 指定 ref 集合，ID 为 `ctx_*` |
| `MentionResolution` | 某个指称指向哪个实体的判断 | 绑定具体 ref |
| `EntityFact` | 实体的背景知识及来源 | 全局实体或上下文实体 |
| `EntityRedirect` | 实体合并后的重定向关系 | 全局、可审计、可撤销 |

## 5. 存储边界

### 5.1 JSONL 只保存确定性实体事实

`EntityAlias/data/*.jsonl` 继续保存：

- 稳定全局实体及 `ent_*` ID；
- 标准名和多语言标准名；
- 确定性别名；
- Wikidata 等外部标识；
- 经核实的基础说明。

这些数据不依赖某篇具体情报，适合人工审查、Git diff 和跨部署复用。

### 5.2 歧义专名解析进入数据库

建议使用独立 MongoDB 集合 `entity_mention_resolutions`，每次指称一条记录：

```json
{
  "mention_id": "mn_*",
  "ref": {
    "subsystem": "news",
    "intelligence_uuid": "...",
    "event_uuid": "...",
    "role": "subject",
    "position": 0
  },
  "surface": "肯尼迪",
  "normalized_surface": "肯尼迪",
  "target_entity_id": "ent_jfk",
  "method": "manual",
  "confidence": 1.0,
  "reason": "...",
  "source_revision": "...",
  "created_at": "...",
  "updated_at": "..."
}
```

目标必须是稳定 `entity_id`，而不是可能变化的标准名或别名字符串。

### 5.3 泛指实体与歧义专名分开存储

泛指实体至少拆为两个集合：

- `contextual_entities`：保存 `ctx_*` 身份、显示名、作用域和说明；
- `contextual_entity_mentions`：保存每个具体指称到 `ctx_*` 的关联。

物理分离的目的，是从数据结构上阻止泛称被误当成全局实体：

```json
{
  "contextual_entity_id": "ctx_*",
  "label": "此次巴黎抗议中的示威者",
  "type": "collective",
  "scope": "event_cluster",
  "created_at": "..."
}
```

```json
{
  "mention_id": "mn_*",
  "ref": {
    "subsystem": "news",
    "intelligence_uuid": "...",
    "event_uuid": "...",
    "role": "subject",
    "position": 0
  },
  "surface": "示威者",
  "target_contextual_entity_id": "ctx_*",
  "method": "manual",
  "confidence": 1.0
}
```

不要在实体文档中维护不断增长的 ref 数组。应采用“一次指称一条关联记录”，通过
`target_entity_id` 或 `target_contextual_entity_id` 反向查询全部情报。这样避免并发更新、
文档膨胀和审计困难。

### 5.4 为什么优先使用 MongoDB

当前情报和事件已经存储在 MongoDB。上下文解析数据需要高频完成两个方向的联立：

- 从一批情报/事件批量取得全部指称解析；
- 从一个实体反查支撑它的全部情报。

MongoDB 可以复用现有运维体系、集合前缀和子系统隔离，无需引入 PostgreSQL 等新依赖；
文档结构也适合解析算法逐步增加证据字段。SQLite 仍适合审计或小型工具，但不适合作为
实体图与 Mongo 事件之间的主联立层。

建议索引：

- `mention_id` 唯一索引；
- `ref.intelligence_uuid`；
- `ref.event_uuid`；
- `(ref.subsystem, ref.intelligence_uuid)`；
- `target_entity_id`；
- `target_contextual_entity_id`；
- `(normalized_surface, target_entity_id)`。

## 6. ref 与 mention 的稳定定位

仅绑定情报 UUID 不总是充分：同一篇文章可能同时出现两个同名人物。因此 ref 至少支持：

```text
subsystem + intelligence_uuid + event_uuid + role + position
```

在落地时应生成稳定 `mention_id`。它可以由上述路径确定性生成，但必须同时保存
`source_revision` 或源片段指纹；如果事件内容后来被重建或槽位顺序变化，系统应把旧解析
标为待复核，而不是静默指向错误位置。

具体的 mention 定位协议、事件修改语义和指纹算法仍属于待讨论项。

## 7. 采用非破坏性解析，不改写原始情报

讨论过两种方案：

1. **破坏性**：把 Event V4 中的实体名称替换为 UUID 引用；
2. **非破坏性**：保留原始抽取，在旁表保存解析关系，读取时形成解析视图。

当前结论是采用非破坏性方案。原因包括：

- 原始名称是 LLM 实际抽取结果，也是判断解析是否合理的重要证据；
- 歧义消解、泛称归组和人工合并以后都可能被推翻；
- 直接替换会破坏 Event V4 的现有存储契约；
- 拆分、撤销和更换权威实体时不应批量改写历史情报；
- 原始数据与解释性投影分离，更符合可追溯的数据处理原则。

读取时可以形成如下解析视图：

```json
{
  "surface": "肯尼迪",
  "resolved_name": "约翰·肯尼迪",
  "entity_id": "ent_jfk"
}
```

如果未来性能不足，可以增加可重建的物化投影或缓存，但该投影不能成为事实源。

## 8. 实体图的身份解析规则

实体图不应继续用“名称 + 类型 + 国家”作为最终身份。每个指称按以下优先级解析：

1. 命中当前 ref 的歧义专名记录：使用 `ent_*`；
2. 命中当前 ref 的泛指关联记录：使用 `ctx_*`；
3. 命中全局确定性别名：使用 `ent_*`；
4. 均未命中：使用带 ref 作用域的临时 `unresolved_*` 节点。

只要多篇情报中的指称解析到同一 `ent_*` 或 `ctx_*`，它们在图上就是同一个点，事件数、
文章数和关系印证据此累计。图仍应展示每条边和节点背后的原始 ref，以便人工核验。

## 9. 带前缀名称与层级实体

不能通过简单删除前缀实现合并，因为前缀可能只是描述，也可能构成新的实体身份：

- “美国总统特朗普”中的“美国总统”是职务上下文，可以帮助解析到特朗普；
- “法国巴黎市”“巴黎”可能是同一地点的不同表述；
- “北京大学医学部”与“北京大学”是上下级实体，不能作为别名合并；
- “中国银行北京分行”与“中国银行”同样应表达隶属关系而非等价关系。

因此应采用“候选生成 + 上下文验证”：识别头衔、地域和上级组织等修饰成分，再结合实体
类型、时间、国家、共现实体和外部 ID 判断是别名、歧义消解线索，还是独立下级实体。

## 10. 实体 Wiki 与地理知识

实体 Wiki 以稳定实体身份为中心，而不是以名称页面为中心。建议逐步展示：

- 标准名、多语言名和确定性别名；
- 类型、简介、外部 ID 和权威来源；
- 首次/最近出现时间、相关情报、事件和关系；
- 人物职务、组织隶属等结构化关系；
- 地点的国家、上级行政区、坐标和地图位置；
- 每条事实的来源、更新时间和核实状态。

地理实体适合作为首个完整 Wiki 类型。外部知识可以从 Wikidata 等来源预填并缓存，本地
核实结果优先。争议地区不能只有一个无来源的“所属国家”，应允许保存多个带来源和
语义的行政、主权或声索关系。

## 11. 人工合并、拆分与作用范围

实体图可以提供多选节点合并，但操作时必须明确作用范围：

1. 只解析当前情报中的一个指称；
2. 解析当前选择的若干情报 ref；
3. 把多个指称归入同一个上下文实体；
4. 合并两个已有全局实体；
5. 确认某名称是全局确定性别名。

前两种写 `entity_mention_resolutions`，第三种写上下文实体及其 mention 关联，第四种写
`EntityRedirect`，只有第五种才修改 JSONL 全局别名。

所有人工治理操作都应支持：

- 合并前预览涉及的名称、类型、国家、关系和支撑情报；
- 记录操作者、时间、理由和影响范围；
- 撤销合并、拆分错误实体和重新指派 ref；
- 阻止或强提醒明显的类型冲突；
- 永久保留原始抽取值。

实体合并优先使用 `old_entity_id -> authoritative_entity_id` 重定向，不直接重写全部历史数据。

## 12. 标准化率应如何衡量和提升

当前覆盖率低有两个直接原因：全局别名数据量很小，以及归档侧只有精确命中才会替换名称。
未来不应只统计“不同字符串中多少进入别名表”，而应分别统计：

- 指称加权的确定性别名命中率；
- 歧义专名已解析率、未解析率和人工/自动来源；
- 泛称识别率、已归组率和受保护未合并率；
- 图节点中 `ent_*`、`ctx_*`、`unresolved_*` 的数量及情报覆盖；
- 人工决定的撤销率和过期解析数量。

提升路径应是：扫描历史和新增情报中的高频未解析指称，形成工作队列；对高置信确定性名称
补入 JSONL，对歧义专名保存 ref 解析，对泛称仅在有证据时归入 `ctx_*`。模糊或向量相似
只用于召回候选，不能单独成为自动合并依据。

## 13. 与当前实现的差距

截至本文日期，现有实现具有以下限制：

- `AliasIndex._exact` 是“一个标准化名称 -> 一个实体”，同名歧义会被冲突校验拒绝；
- Event V4 后处理只对已登记的精确名称替换为标准名；
- 查询层只进行确定性别名展开；
- `SituationViews` 实体图按名称、类型和国家临时组成节点 ID，尚未接入稳定实体 ID；
- 没有 mention 级 ref、上下文实体、解析审计、实体重定向和人工图治理；
- 当前 JSONL 仅有少量实体，不能代表可用的标准化覆盖。

因此本文描述的是下一阶段架构，不得把它视为当前已经具备的运行能力。

## 14. 暂定实施顺序

以下顺序只作为后续落地讨论的起点：

1. 定义稳定 mention/ref 协议和三类集合契约；
2. 实现非破坏性解析存储、反向查询和审计；
3. 让实体图优先使用 `ent_*` / `ctx_*`，未解析节点保持 ref 作用域；
4. 实现图上的 ref 级解析、上下文归组、实体合并及撤销；
5. 改造全局名称索引，使歧义名可以召回多个候选但不能自动唯一解析；
6. 建立高频未解析指称工作队列和历史投影重建；
7. 建设实体 Wiki，先完善地理实体；
8. 在数据和人工反馈充分后，再引入自动上下文消歧。

## 15. 后续仍需讨论的落地问题

1. `mention_id` 的稳定生成规则以及 Event V4 中角色槽的定位方式；
2. 三类 Mongo 集合是全局集合带 `subsystem`，还是沿用子系统集合前缀；
3. 原始事件修订后如何识别并处理过期解析；
4. `ctx_*` 的允许作用域、跨文章归组条件和生命周期；
5. 图查询时实时联立还是维护可重建物化投影；
6. 全局实体合并重定向、拆分和循环检测协议；
7. 自动解析的置信阈值、证据结构和人工复核流程；
8. 实体 Wiki 的事实模型、本地覆盖规则和外部数据更新策略；
9. 如何在不改变 Event V4 权威抽取契约的前提下向其他子系统提供统一解析视图。
